1. Introduction

1.1 Purpose

This document describes the software requirements for the EN2H Booking Platform REST API — a backend system enabling customers to book services and allowing staff/admin users to manage those services and bookings.

1.2 Intended Audience

  • Backend engineers reviewing or extending the codebase
  • EN2H assessment evaluators
  • Frontend developers integrating with this API

1.3 Overview

The system exposes a RESTful API with three core modules: Authentication, Service Management, and Booking Management. It enforces strict business rules, provides standardised error responses, and is fully documented via Swagger UI.

4. System Architecture

4.1 Module Structure

src/ ├── main.ts # Bootstrap: global prefix, pipes, filter, Swagger, CORS ├── app.module.ts # Root module — imports all feature modules ├── prisma/ # Global PrismaModule + PrismaService (driver adapter) ├── auth/ # Authentication: JWT strategy, guards, register/login/refresh ├── services/ # Service CRUD: controller, service, DTOs ├── bookings/ # Booking management: controller, service, DTOs, business rules └── common/ └── filters/ # GlobalExceptionFilter — standardised JSON error format

4.2 Request Lifecycle

  1. Request arrives at NestJS HTTP server
  2. ValidationPipe validates and transforms the DTO (whitelist + forbidNonWhitelisted)
  3. JwtAuthGuard (if protected route) verifies Bearer token via JwtStrategy
  4. Controller delegates to Service layer
  5. Service applies business rules and calls PrismaService
  6. PrismaService executes the query via @prisma/adapter-pg against Neon PostgreSQL
  7. Response serialised and returned; GlobalExceptionFilter catches any errors

8. Authentication & Authorization

  • Strategy: JWT Bearer tokens via @nestjs/jwt + Passport.js
  • Access Token: Short-lived (15 minutes), used for protected API calls
  • Refresh Token: Long-lived (7 days), used only to obtain a new access token
  • Password hashing: bcrypt with 12 salt rounds
  • Protected endpoints: Guarded by JwtAuthGuard — validates token and user existence in DB

9. Input Validation

All request bodies are validated using class-validator decorators on DTO classes. The global ValidationPipe is configured with:

  • whitelist: true — strips unknown properties
  • forbidNonWhitelisted: true — throws error on unknown properties
  • transform: true — auto-transforms payloads to typed DTO instances

A GlobalExceptionFilter catches all exceptions and transforms them to a consistent JSON shape:

12. Assumptions Made

  1. Two-role model: Admin/Staff (JWT-authenticated) and Customers (unauthenticated public access).
  2. Soft delete: Services are never hard-deleted; isActive=false preserves booking history.
  3. Booking time as string: bookingTime is stored as HH:MM — timezone handling was not specified.
  4. No ownership verification for cancellation: Customers cancel using the booking ID alone; OTP verification is out of scope.
  5. Two Neon URLs: Pooled URL for runtime, direct URL for migrations (Neon serverless requirement).
  6. No email notifications: Not specified in the assessment requirements.
  7. UUID primary keys: Used for all models — better security and distributed compatibility vs. auto-increment integers.
  8. Pagination defaults: page=1, limit=10 when not specified.
